# رفع النظام على دومين واستضافة — خطوة بخطوة

الطريقة: **خادم واحد (VPS)** يعمل عليه كل شيء داخل Docker:
التطبيق + قاعدة البيانات + شهادة HTTPS تلقائية (Caddy) + نسخة احتياطية يومية.

> الملفات الجاهزة في المستودع: `Dockerfile`، `docker-compose.yml`، `deploy/Caddyfile`، `deploy/env.production.example`.

---

## 1) ما تحتاج شراءه

| البند | المواصفات المقترحة |
|---|---|
| خادم VPS | Ubuntu 24.04، معالج 2 vCPU، ذاكرة 4GB، مساحة 40GB على الأقل. (مثل Hetzner أو DigitalOcean أو مزود سعودي) |
| دومين | مثل `pamperme.sa`، ويُفضّل نطاق فرعي للنظام مثل `app.pamperme.sa` |

> **بيانات العميلات:** النظام يحفظ أسماء وأرقام وعناوين عميلات ورواتب. راجعوا متطلبات نظام حماية البيانات الشخصية في السعودية (PDPL) عند اختيار مكان الخادم؛ الاستضافة داخل المملكة قد تكون الأنسب. (هذه ملاحظة وليست استشارة قانونية.)

## 2) ربط الدومين بالخادم

من لوحة الدومين (DNS) أضف سجلًا:

| النوع | الاسم | القيمة |
|---|---|---|
| `A` | `app` | عنوان IP الخادم |

انتظر حتى يعمل (عادة دقائق، وأحيانًا حتى ساعات).

## 3) تجهيز الخادم (مرة واحدة)

ادخل للخادم عبر SSH (من الكمبيوتر: `ssh root@عنوان_IP`) ثم نفّذ:

```bash
curl -fsSL https://get.docker.com | sh
ufw allow 22 && ufw allow 80 && ufw allow 443 && ufw --force enable
git clone https://github.com/tafra2026/system.git /opt/pamper
cd /opt/pamper
```

- المستودع خاص، فعند `git clone` سيطلب:
  - **Username:** اسم حسابك على GitHub.
  - **Password:** ليس كلمة مرور GitHub، بل **Token** تنشئه من GitHub: Settings ← Developer settings ← Fine-grained tokens ← Generate، اختر المستودع `tafra2026/system` وصلاحية **Contents: Read-only**.

## 4) الإعدادات السرية (على الخادم فقط)

```bash
cp deploy/env.production.example .env
openssl rand -base64 32
nano .env
```

- انسخ الناتج الطويل من الأمر الثاني وضعه بعد `POSTGRES_PASSWORD=`.
- اكتب الدومين بعد `DOMAIN=` بدون https، مثل `DOMAIN=app.pamperme.sa`.
- احفظ واخرج من nano: `Ctrl+O` ثم `Enter` ثم `Ctrl+X`.

> ملف `.env` لا يُرفع إلى GitHub ولا يُرسل في المحادثات.

## 5) البناء ومفاتيح إشعارات الجوال

```bash
docker compose build
docker compose run --rm --no-deps app npm run -s push:keys
```

- البناء يستغرق عدة دقائق في أول مرة.
- الأمر الثاني يطبع 3 أسطر تبدأ بـ `VAPID_`. افتح `nano .env` واستبدل أسطر `VAPID_` الثلاثة بها، واكتب بريدك مكان `CHANGE_ME@your-domain`.
- هذه المفاتيح تُولَّد **مرة واحدة فقط**. لا تغيّرها بعد ذلك، وإلا سيحتاج كل موظف لتفعيل الإشعارات من جديد.

## 6) التشغيل

```bash
docker compose up -d
docker compose ps
```

- يجب أن تظهر كل الخدمات `Up` أو `running`: `db`، `app`، `worker`، `caddy`، `backup`.
- تحديثات قاعدة البيانات تُطبّق تلقائيًا.
- شهادة HTTPS تصدر تلقائيًا خلال دقيقة أو اثنتين بعد أن يشير الدومين للخادم.

## 6-ب) البيانات الأساسية وأول حساب (المالكة)

```bash
docker compose exec app npm run db:seed
docker compose exec app npm run account:create -- --role=owner --username=doha
```

- الأمر الأول يضيف الموظفين الثمانية والخدمات والباقات ونقطة الانطلاق، وهو آمن للتكرار.
- الأمر الثاني يطلب كلمة المرور مرتين، ولا تظهر أثناء الكتابة. هذا طبيعي.

الآن افتح `https://app.pamperme.sa` وسجّل الدخول باسم المستخدم `doha` وكلمة المرور التي كتبتها.

## 7) حسابات باقي الموظفين (من داخل التطبيق)

**الموظفون ← اختر الموظف ← حساب الدخول:**
1. اكتب اسم المستخدم (إنجليزي صغير، مثل `alaa`).
2. اكتب كلمة مرور (10 أحرف على الأقل) وأعدها للتأكيد.
3. الخيار «يغيّرها الموظف بنفسه عند أول دخول» مفعّل افتراضيًا (مستحسن).
4. «إنشاء الحساب»، ثم سلّم البيانات للموظف **بشكل خاص**.

- نسي كلمة المرور؟ من نفس المكان: «تعيين كلمة مرور جديدة».
- نسيت المالكة كلمة مرورها؟ على الخادم:
  `docker compose exec app npm run account:create -- --role=owner`
- موظف غادر؟ «إيقاف الحساب» (لا يُحذف تاريخه).

## 7-ب) إشعارات الجوال لكل موظف

كل موظف يفعّلها بنفسه من جهازه: **حسابي ← إشعارات الجوال ← تفعيل الإشعارات** ثم «سماح».
- **آيفون:** لازم أولًا من Safari: «مشاركة» ← «إضافة إلى الشاشة الرئيسية»، ويفتح التطبيق من الأيقونة (iOS 16.4 أو أحدث)، وبعدها يفعّل.
- **أندرويد والكمبيوتر:** من Chrome مباشرة.
- زر «إرسال إشعار تجريبي» يتأكد أنها تعمل.
- لو الإشعارات لم تصل لأي سبب: كل التنبيهات موجودة دائمًا في صفحة الإشعارات (الجرس أعلى الشاشة).
- التذكيرات تعمل من الخادم (خدمة `worker`) حتى لو كل الصفحات مغلقة.

## 8) التحديث عند وجود نسخة جديدة

```bash
cd /opt/pamper
git pull
docker compose build
docker compose up -d
```

## 9) النسخ الاحتياطي

- نسخة تلقائية كل يوم في المجلد `/opt/pamper/backups`، وتُحذف النسخ الأقدم من 30 يومًا.
- **انسخها خارج الخادم أيضًا** (مثلًا أسبوعيًا إلى تخزين مشفّر)، لأن الخادم نفسه قد يتعطل.
- نسخة فورية يدويًا:
  ```bash
  docker compose exec -T db pg_dump -U pamper -Fc pamper > backups/manual-$(date +%Y%m%d).dump
  ```
- الاستعادة (تمسح البيانات الحالية وتضع النسخة مكانها):
  ```bash
  docker compose exec -T db pg_restore -U pamper -d pamper --clean --if-exists < backups/pamper-XXXX.dump
  ```
- جرّب الاستعادة على خادم تجريبي مرة كل شهر.

## 10) أوامر مفيدة

| المطلوب | الأمر |
|---|---|
| حالة الخدمات | `docker compose ps` |
| سجل التطبيق | `docker compose logs -f app` |
| سجل شهادة HTTPS | `docker compose logs caddy` |
| سجل الإشعارات والتذكيرات | `docker compose logs -f worker` |
| إعادة التشغيل | `docker compose restart app` |
| إيقاف الكل | `docker compose down` (البيانات تبقى) |

## 11) استضافة بدون Docker (لوحة Node.js) أو خادم بـ glibc قديم

**العَرَض:** أثناء البناء يظهر `GLIBC_2.29 not found` ثم `Failed to load SWC binary` أو `Cannot find module …next.config`.

**السبب:** مُترجِم Next.js الأصلي (SWC) يحتاج glibc 2.30 أو أحدث. الخوادم الأقدم (مثل Hostinger أو CloudLinux/AlmaLinux 8، glibc 2.28) لا تستطيع تحميله. ومُجمِّع Turbopack (الافتراضي في Next 16) لا يعمل بدونه.

**الحل المعتمد:**
- أمر البناء في المشروع أصبح `next build --webpack`. هذا المُجمِّع يعمل بنسخة WebAssembly من المُترجِم عند فشل النسخة الأصلية.
- حزمة WebAssembly (`@next/swc-wasm-nodejs` بنفس إصدار Next) مثبّتة ضمن المشروع، فلا يُعتمد على تنزيلها أثناء البناء.
- مُختبر على AlmaLinux 8 (glibc 2.28): البناء يستغرق حوالي دقيقة، والتشغيل والدخول والصفحات ورفع الصور والعامل الخلفي كلها تعمل.

**الطريقة (أ) — البناء على الاستضافة نفسها (Hostinger):**
1. اربط المستودع أو ارفع الملفات كالمعتاد.
2. **أمر التثبيت:** `npm install` أو `npm ci`. يجب أن تُثبَّت devDependencies أيضًا، لأنها لازمة للبناء وللأمر `tsx`. لذلك لا تضع `NODE_ENV=production` أثناء التثبيت إن كانت اللوحة تفصل بينهما.
3. **أمر البناء:** `npm run build`.
4. ثم تابع من الخطوة 3 أدناه (أمر التشغيل والمتغيرات)، مع تجاهل ملاحظة «اترك أمر البناء فارغًا».

**الطريقة (ب) — حزمة جاهزة (إن لم تسمح الاستضافة بالبناء):**
1. في GitHub افتح **Actions ← Build deploy bundle**. يعمل تلقائيًا مع كل تحديث، أو من «Run workflow». نزّل الملف `pamper-app-….zip` من قسم **Artifacts**، وبداخله `pamper-app.tar.gz`.
   - أو ابنه بنفسك على جهاز Linux حديث عليه Node 22: `bash scripts/build-bundle.sh`.
2. ارفع `pamper-app.tar.gz` للخادم وفكّه في مجلد التطبيق.
3. في لوحة الاستضافة:
   - **Node.js:** 22.
   - **أمر البناء (Build):** في الطريقة (أ): `npm run build`. في الطريقة (ب): اتركه فارغًا أو عطّله، لأن الحزمة مبنية مسبقًا ولا تحتاج `npm install` ولا `npm run build`.
   - **أمر التشغيل (Start):** `npm run start:host` أو `npm start`. تحديثات قاعدة البيانات تُطبق أيضًا من داخل التطبيق عند بدء تشغيله (حتى لو شغّلته اللوحة بطريقتها الخاصة)، مع قفل يمنع تطبيقها مرتين. في السجل يظهر `Migrations applied.` أو `Database update failed: …`. لإيقاف ذلك: `MIGRATE_ON_START=0`.
   - سطور `Error: Server is not running` مع تكرار `Ready` في سجل Hostinger تظهر عندما تُوقف اللوحة عملية وتشغّل غيرها، ولا تعني وحدها أن الموقع متوقف.
   - رسائل `Attempted to load @next/swc-linux-x64-gnu ... GLIBC_2.29 not found` أثناء البناء **تحذيرات عادية** على هذه الاستضافة: يستخدم البناء نسخة WebAssembly بدلًا منها، والبناء ينجح (آخره قائمة الصفحات Route).
   - **متغيرات البيئة:**

     | المتغير | القيمة |
     |---|---|
     | `DATABASE_URL` | رابط PostgreSQL (الإصدار 13 أو أحدث، ويُسمح بإضافة `btree_gist`) |
     | `APP_BASE_URL` | `https://test.tafraa.com` |
     | `NODE_ENV` / `APP_ENV` | `production` |
     | `RUN_WORKER_IN_APP` | `1` (التذكيرات وإشعارات الجوال تعمل داخل نفس التطبيق) |
     | `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` | من `npm run -s push:keys` (مرة واحدة) |
     | `PORT` | عادة تضبطه اللوحة تلقائيًا |

4. من «Terminal» في اللوحة (داخل مجلد التطبيق)، مرة واحدة:
   ```bash
   npm run -s push:keys
   npm run db:seed
   npm run account:create -- --role=owner --username=doha
   ```

**متطلبات الخادم:**
- glibc 2.28 أو أحدث (`ldd --version`).
- Node.js 22.
- قاعدة PostgreSQL.
- HTTPS على الدومين (تقدمه اللوحة عادة).
- النسخ الاحتياطي لقاعدة البيانات مسؤولية مزود الاستضافة أو قاعدة البيانات في هذه الحالة.

## 12) تحديث سبتمبر 2026 — خطوات آمنة وخطة التراجع

**تحديثات قاعدة البيانات (0015–0022) إضافية فقط:** أعمدة وجداول وفهارس جديدة وقيم جديدة للحالات. لا حذف ولا مسح لأي بيانات، ولا reset ولا seed. تُطبق تلقائيًا عند التشغيل (`npm run start:host` أو Docker).

| الملف | المحتوى |
|---|---|
| 0015 | حالة «ملغي» وأعمدة سبب/وقت الإلغاء |
| 0016–0017 | جداول روابط الدفع وإشعاراتها + قيود عدم التعديل |
| 0018 | صورة المبنى على الطلب + النسخة المصغرة (مع نسخ الصور الحالية للطلبات) |
| 0019–0020 | مستندات العميلات (PDF) وروابطها + الترقيم + قيد عدم التعديل |
| 0021 | أوقات خطوات السائق |
| 0022 | إضافة `pg_trgm` ودالة توحيد الحروف العربية وفهارس البحث |

> التحديثات كلها تُطبق في عملية واحدة: إن فشل أي منها لا يُطبق شيء وتبقى القاعدة كما كانت، ولا يبدأ التطبيق (لأن `start:host` يطبق التحديثات قبل التشغيل) — عندها أعد نشر النسخة السابقة. إضافة `pg_trgm` مدعومة في Neon.

**قبل التحديث (إلزامي):**
1. غيّر كلمة مرور قاعدة البيانات (سبق مشاركة بيانات اتصال) وحدّث `DATABASE_URL` في إعدادات الاستضافة فقط.
2. خذ نسخة احتياطية / فرع (Branch) من قاعدة Neon قبل النشر.
3. أضف المتغيرات الجديدة (اختيارية؛ بدونها تعمل الميزات بالطريقة اليدوية): `GOOGLE_MAPS_BROWSER_KEY`، `PAYMOB_SECRET_KEY`، `PAYMOB_PUBLIC_KEY`، `PAYMOB_HMAC_SECRET`، `PAYMOB_INTEGRATIONS`، `PAYMOB_BASE_URL`.
4. جرّب أولًا على بيئة الاختبار (test.tafraa.com) مع فرع قاعدة منفصل إن أمكن.

**بعد التحديث — فحص سريع:** الدخول بكل دور، فتح «الطلبات»، فتح طلب وإصدار PDF، شاشة السائق، البحث بالحي، صفحة «تجهيز التطبيق».

**التراجع (Rollback):**
- الكود: أعد نشر النسخة السابقة (الـ commit السابق `0cc33e9`).
- قاعدة البيانات: التحديثات إضافية، والنسخة السابقة تعمل معها **ما لم يوجد طلب أو زيارة بحالة «ملغي»** أو دفعة بطريقة `paymob` (النسخة القديمة لا تعرف هذه القيم وقد تظهر خطأ في تلك الصفحات). إن حدث ذلك: الرجوع لفرع/نسخة Neon المأخوذة قبل التحديث (يفقد ما أُدخل بعده) — لذلك يُفضل التراجع بسرعة أو إصلاح الخطأ للأمام.
- لا تحذف الأعمدة أو الجداول الجديدة يدويًا.

## ما تم اختباره وما لم يُختبر بعد

- ✅ صورة التطبيق تُبنى وتعمل: تحديث قاعدة البيانات تلقائيًا، التهيئة، إنشاء حساب المالكة، تسجيل الدخول.
- ⏳ تشغيل Caddy وشهادة HTTPS الحقيقية تُختبر على الخادم الفعلي مع الدومين (تحتاج دومين حقيقي يشير للخادم).
- ⏳ تابي وتمارا: ما زالت تُسجل يدويًا حتى تفعيل التكامل.
- ⏳ Paymob: مبني ومختبر بمحاكاة تطويرية فقط؛ يحتاج مفاتيح وتجربة في بيئة الاختبار.
- ⏳ خريطة Google داخل الحجز: تحتاج `GOOGLE_MAPS_BROWSER_KEY`؛ لم تُختبر بمفتاح حقيقي.
- ⏳ لم يُختبر على آيفون حقيقي؛ الفحص تم بمتصفح Chromium بمقاسات 360–1440.
- ⏳ وصول إشعارات الجوال فعليًا لآيفون وأندرويد يُختبر بعد النشر على الدومين (يحتاج HTTPS حقيقي). المنطق نفسه مختبر آليًا بمحاكاة تطويرية لا ترسل شيئًا.

> قبل الاعتماد الكامل: تجربة أسبوع مع الفريق على بيانات تجريبية (`is_test`)، ثم البدء بالبيانات الحقيقية.
